# Review checklist

The student is a PM, not an engineer. They want a quick, honest read of whether a brief is ready to show someone. Use plain English.

## 1. Find the brief

- If the student named a file, use it.
- If they didn't, and there's one obvious brief in the folder they're working in (a file with "brief" in its name), use that and say which one.
- If there are several, or none, ask one short question: "Which brief should I check?"

Read the whole brief before judging anything. Only check the brief itself. Don't pull in other files, wiki pages or data unless the student asks.

## 2. Run the four checks

Give each check **Pass**, **Partly** or **Fail**. Back every verdict with a short quote from the brief (or say plainly that nothing in it covers this).

**1. Names who owns it**
- Pass: one named person or team is clearly responsible for the work going ahead.
- Partly: an owner is implied, split between people, listed as a question ("Who owns this?"), or recorded differently in different places.
- Fail: no owner anywhere.
- Owners of individual open questions don't count as the owner of the brief.

**2. Says how we'll know it worked**
- Pass: specific signs of success that someone could actually check later, ideally with a number, a starting point and a target ("misses fall from about 15% to 2–3%").
- Partly: success is described but vague ("handlers are happier"), has no baseline, or nobody could measure it with the data we have.
- Fail: no success measures.

**3. Keeps the same scope start to finish**
- Compare what the opening promises, what the "build" section lists, the success measures, the "not doing" list, the risks and the open questions.
- Flag anything that is built but never measured, measured but never built, promised early and dropped later, ruled out in one place but included in another, or that quietly grows (one responder in the problem, every responder in the fix, with no explanation).
- Pass: everything lines up. Partly: small drift. Fail: the end describes a different project from the start.

**4. Explains the problem before the fix**
- Pass: the brief says who is hurt, how, and with what evidence before it proposes anything.
- Partly: the problem is there but comes after the solution, or is only stated as the absence of the solution ("we don't have alerts").
- Fail: it opens with the solution and never really says what's wrong.

## 3. Report back

Keep it short:

| Check | Result | Why (quote or "not found") |
|---|---|---|
| Names who owns it | … | … |
| Says how we'll know it worked | … | … |
| Same scope start to finish | … | … |
| Problem before the fix | … | … |

Then **"To fix"**: one plain sentence for each check that isn't a Pass, saying what to add or change and where in the brief. Finish with one line saying whether the brief is ready to share.

## Rules

- Don't edit the brief. Offer to make the fixes, and only make them if the student says yes.
- Don't invent facts to fill gaps (an owner, a number). If something is missing, say it's missing.
- Don't save anything to memory or outside the course folder.
